* Scope and acceptance verdict

This v1370 review examines the installed-review-tree candidates from v1362
through v1369. It is a *DOCUMENT-ONLY* source and evidence checkpoint: it does
not change runtime assembly, public APIs, proof status, certificate admission,
transaction authority, or the implementation of any proof rule.

Verdict:

  *RESTRICTED, CONDITIONAL DECLARED-MACHINE INDUCTION AND SOURCE-RELATIVE
  OBSERVED-WRITER ACCOUNTING ACCEPTED; PHYSICAL APPLICATION COMPLETENESS,
  EXECUTABLE REFINEMENT, AND UNIVERSAL SOUNDNESS REMAIN OPEN.*

The positive claim is intentionally narrow. For the enumerated initial states
and exactly the declared abstract operations, Gesso can assemble conditional
base/step premises for mathematical induction. Declared literal initializers
can be compared with that finite initial-state base. The newer assembly bridge
can recheck an issued application and a supplied current host-observed routing
snapshot, and it can compare operation identifiers across the two catalogs.

None of this establishes that the host has enumerated every actual physical
writer, that an identifier-matched handler realizes its abstract transition,
that a physical XTDB snapshot is authenticated, or that the underlying
Clojure checkers are independently proved sound. The v1368 per-writer ledger
records nine such proof obligations; it discharges *zero* of them.

The review tree is based on Git HEAD =e65820e= plus delivered installation
files overlaid separately. Git HEAD alone does not identify those overlays or
prove that the user's own repository has installed them. All eight v1362--v1369
source/test payloads in this review tree match their original published
installation TAR members byte-for-byte. The full Ygg/Shard, browser,
ClojureScript, and live XTDB integration gates were NOT executed for v1370.

* The exact conditional theorem we are approaching

** Finite declared abstract induction

Let =B= be the finite *enumerated* abstract initial-state set, =O= the
*declared* abstract operation set, =I= the typed invariant, and =T_o= the
abstract transition relation for an operation =o=.

The desired premises are:

#+begin_example
  (Base)  for every b in B: I(b)
  (Step)  for every o in O, every s,x,s':
            I(s) AND T_o(s,x,s')  =>  I(s')
#+end_example

If the transition interpretation and conditional preservation rules are
sound, ordinary induction then yields:

#+begin_example
  for every finite sequence
    s0 --o1/x1--> s1 --o2/x2--> ... --on/xn--> sn
  beginning in B and using only matching operations from O:
    for every k in [0,n], I(sk).
#+end_example

This conclusion is about the declared abstract machine. It does not need a
fixed bound on history length as a *mathematical* induction schema; the
current executable =audit-finite-history!= independently checks individual
history *witnesses* with a limit of 128 steps. Those are different claims.

The implementation's finite source checks are evidence for the premises; the
universal soundness of the implementing typed evaluator, transition checker,
and preservation inference families is a separate, still-open obligation.

** Conditional declared-initializer image

Let =C= be a declared catalog of *total literal constructors*, each with one
instruction for every projected state field. Its denotation is exactly one
abstract state per constructor; a present =nil= is distinct from =[:absent]=.

#+begin_example
  Image(C) = { denote(c) | c in C }
  every declared constructor starts in B  iff  Image(C) subset-of B
#+end_example

Equality of =Image(C)= and =B= is stronger source bookkeeping, but *subset*
coverage is sufficient for the conditional starting-state argument. Neither
relationship establishes that all deployed constructors or ad hoc writers
are included in =C=.

** Additional bridge required for actual applications

To promote declared induction to a claim about actual application behavior,
we would need evidence for the following separate implication:

#+begin_example
  Every physically admitted initialization maps into B,
  AND every physically executable write maps to some o in O,
  AND every actual execution of that writer refines T_o,
  AND the invariant projection reflects the physical state claimed,
  AND the premises and implementation of the checker are sound.

  Therefore every covered physical execution preserves I.
#+end_example

The v1366 current-snapshot operation-ID join and v1368 obligation inventory
are necessary engineering inputs to this bridge; *neither proves it*.

* Trust-boundary analysis

** What can be safely reused

The following are conditional, source-grounded engineering products:

1. Exact enumerated initial-state and declared operation coverage.
2. Typed, guarded, independent finite abstract-history witnesses.
3. Literal constructor images and source-relative subset/exact checks.
4. Observed operation-ID and current issued handler/route joins relative to
   the host enumeration actually supplied.
5. Source-derived executable writer obligation inventories, including
   explicit abstract input/read/write/frame contracts and assignment origins.
6. Diagnostics that fail closed on malformed source and substituted or stale
   report evidence in the covered in-process threat model.

** What an apparently clean catalog still cannot prove

- *Unobserved writers:* A direct XTDB call, a nonroute task, a foreign
  component, or an entry point omitted by the host enumerator may mutate
  protected state without appearing in the source-relative observed catalog.
- *Handler equivalence:* A checked handler/operation ID does not show that
  its real authorization, guards, read/write effects, and versions implement
  the independent v1362 abstract relation.
- *Initializer completeness:* A perfect image of declared literal
  constructors is insufficient if another initialization path can create
  the same domain entities.
- *Projection completeness:* The declared finite field projection does not
  automatically describe every physical document/table/field that a writer
  can change. Correct frame reasoning needs an appropriate physical domain.
- *Transaction provenance:* A post-hoc or caller-supplied before/after map
  is not authenticated evidence of the transaction's internal read basis,
  predicates, atomic commit, or outcome.
- *Deployment closure:* Checking a current in-memory router is not proof
  that the deployed router and all execution entry points use that snapshot
  and remain stable until replaced under controlled admission.
- *Checker metatheorem:* Two agreeing executable interpreters or a checked
  proof-report shape do not establish universal soundness of the Clojure
  algorithms implementing S1, S2, S4, and induction.
- *Browser/HTMX/SSE refinement:* UI progression and commit-unknown handling
  remain separate behavioral boundaries; abstract server safety does not
  itself prove client observational equivalence.

** Explicit counterexamples to invalid promotion

1. =Image(C) subset-of B= and all =I(b)= hold, but a hidden import path
   initializes a state outside =B=. Declared initializer coverage remains
   true; real initializer completeness is false.
2. Every observed route has a matching operation ID, but a background job
   can write the same XTDB field. The ID join remains true; physical writer
   closure is false.
3. An issued handler uses the expected operation keyword but reads an old
   version without an atomic compare-and-set. The ID join is true; transition
   and serial-concurrency refinement may fail.
4. A sample transaction's final fields match the abstract assignment, but
   an unmodeled physical field was altered. One projected witness matches;
   complete frame preservation has not been established.
5. A complete v1368 ledger of nine rows is copied and all statuses are
   replaced with =:discharged=. That modified data is neither authoritative
   evidence nor a successful result of the source-checked function.

* Next implementation steps after v1370

** v1371: Physical execution provenance boundary (priority)

Define source-derived physical observation obligations around real XTDB
transaction lifetimes, not merely arbitrary caller-provided before/after
maps. Bind observed execution identifiers to checked plan, session, input
projection, transaction-internal basis, write set, and outcome. Initially
keep physical authentication and universal refinement explicitly OPEN.

** Subsequent narrow steps

1. Add permanent negative tests that distinguish authentic transaction
   envelopes from fabricated or stale observations, without making a test
   fixture itself a trusted production witness.
2. Connect actual transaction-internal reads and guard/authorization
   evaluations with the abstract =T(s,x,s')= inputs and pre-state.
3. Check complete physical write and frame footprints, including fields
   beyond the current invariant projection; require an explicit domain
   boundary for any claim of completeness.
4. Model compare-and-set/version checking and atomic commit behavior,
   including conflicts, rejections, unknown commits, and eventual outcome
   incorporation under the supported XTDB execution contract.
5. Create an independently justified refinement rule or trusted small
   checker which consumes authenticated evidence and makes the assumptions
   and proof obligations explicit. It must reject all unsupported sources.
6. Link the actual deployed router/handler and nonroute writer inventory
   to the current issued source, with a credible completeness assumption or
   enforced writer boundary.
7. Preserve the separation between executable semantic core, independently
   justified proof/checker kernel, bounded regression evidence, and final
   admission authority. Application authors should declare Gesso rules, not
   write TLA+, Quint, or Recife specifications manually.

** Proposed release/admission gate

A future assurance admission gate SHOULD require all the following, with no
implicit downgrade or report-based authority escalation:

#+begin_example
  admitted original sources
  AND accepted typed/abstract semantics and soundness evidence
  AND all initializers and writers accounted for in the protected domain
  AND each writer's physical transition refinement established
  AND authenticated deployment/transaction provenance
  AND explicit handling of conflicts and unknown outcomes
  AND current, source-bound, independently checked certificate policy
#+end_example

Every absent premise must produce a typed OPEN or REJECTED result; it must
not be renamed =proved=, =certified=, or =admitted= to unblock execution.

* Final checkpoint decision

v1362--v1369 meaningfully connect finite declared induction, source-derived
literal initialization, current checked application operation identities,
and the exact correspondence obligations needed for executable writers.
These are coherent components of Gesso's intended proof-backed assembly
system, and they now have dedicated permanent adversarial test suites.

They establish a *conditional declared-machine safety argument*, not an
independent universal theorem and not end-to-end proof over physical
application executions. The next highest-value work is authentic,
transaction-internal executable correspondence and a small independently
justified checker, rather than adding another layer of trusted diagnostic
reports without reducing those open assumptions.
