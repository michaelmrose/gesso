* Scope and disposition

This is a *document-only* checkpoint following v1394. It consolidates the
single-node acquisition work begun after the v1381 physical-execution
checkpoint, using the local implementation of v1382–v1394 and the available
focused test results. It does not change an executor, XTDB adapter, application
preflight gate, proof constructor, or certification policy.

*Decision: ACCEPT the acquisition chain as stronger BOUNDED DIAGNOSTIC
EVIDENCE, but DO NOT ACCEPT it as trusted physical execution attestation.*

In particular, v1394 can obtain controlled-executor, typed-input,
application-guard, adapter-call, and later transaction-ledger observations
inside *one synchronous process-local invocation*. This is more persuasive
than correlating independently supplied reports after the fact. It is not an
unforgeable record of the payload accepted by XTDB, transaction causality,
transaction-internal prestate, deployed handler adoption, or universal
physical refinement.

All nine original per-writer physical-refinement obligations remain open.
All nine additional diagnostic acquisition open-obligation labels remain open.
No source in this checkpoint is authorized to issue a physical certificate.

** Out of scope

- HumanHelp application acceptance and production Claim certification.
- Multi-node publication, consistency, failover, or distributed coordination.
- Universal proof-kernel soundness, currently a separate assurance workstream.
- Browser/HTMX/SSE formal refinement, though browser tests remain essential.
- User-visible formal-language authoring. Recife/TLC remains internal finite
  model checking; downstream apps need no Recife, Quint, or TLA+ model.

* Acquisition boundaries and permissible claims

** A. Controlled executor and typed inputs (v1382–v1385)

The controller creates and completes its own one-invocation observation
session, rejects preinstalled observation hooks and substituted entry points,
and hides observer-bearing context from registered application callbacks.
Each attempt has its own identity; the controller neither retries nor
reconstructs the authoritative transaction result.

The v1384 typed-input extension gets the typed declaration from the checked
abstract operation rather than a caller-supplied schema, checks a closed path
projection, and compares it to a second construction-site observation.

The *path mapping is application-supplied*. Even a type-correct match can
project the semantically wrong value, such as treating an operation keyword
as the principal. This is checked correspondence of supplied representations,
not authenticated HTTP principal identity or universal request binding.

=run-controlled-submit!= and =run-controlled-typed-submit!= retain the
original resolution and sensitive plan details in private server-side
results. Their diagnostics must not be copied wholesale to logs or returned
as HTTP data. An incomplete observer capture remains missing evidence.

** B. Transaction-internal basis (v1386–v1387)

The installed XTDB 2.2.0-beta1 public query API accepts snapshot tokens for
external reads. The controlled embedded-XTDB investigation demonstrated that
a pinned external read can remain on revision 1 after revision 2 commits,
whereas an intervening write's =ASSERT= evaluates against the newer state,
not against a supplied stale read token. A query for =SHOW SNAPSHOT_TOKEN=
inside the DML transaction is unsupported in that tested environment.

Do not relabel a before/after pinned read, =xt.txs= ledger observation, or
caller-supplied snapshot as *the write transaction's internal prestate*.
The later single-node serial-history approach is a prospective proof route,
conditional on independently justified XTDB transaction semantics and complete
operation/writer mediation. It has not yet been established.

** C. Guard links and physical authorization (v1388–v1389)

The v1388 diagnostic obtains declared abstract guard readers from the checked
induction/writer source, observes the registered =:predicate-contract!=
callback, and compares linked required guards against the prepared transaction
plan. Missing, altered or incomplete links fail before unsupported claims
are made. The mechanism distinguishes declared dependency guards from
update/CAS conditions.

The links between abstract readers and physical predicate checks are still
application-supplied. Matching checks in a prepared plan do not prove policy
equivalence, the identity of an authorized principal, or that XTDB evaluated
the asserted predicates for a particular committed attempt.

** D. Adapter submission boundary (v1390–v1391)

=gesso.live.consistency.xtdb/capture-tx-api-calls!= observes the actual
adapter call sites for =submit-tx= and =execute-tx= when invoked within the
instrumented path. It records an =:invoked= event and a =:returned= or
=:threw= event for each captured call, preserving the ordered XTDB operations,
filtered options, and call identifier. The ordinary transaction path remains
unchanged when capture is absent.

The captured operation vector is stronger evidence than a caller-reported
vector. Nonetheless, this is *process-local instrumentation of a bound API
function*, not an XTDB-signed payload receipt. An alternate writer or a
substituted function can bypass or impersonate this boundary. Multiple calls,
missing events, and nested captures are explicitly not equivalent to one
verified physical submission. A failure of a later debug callback must not
retroactively change the recorded API return into an API exception.

** E. Transaction identity and later ledger read (v1392–v1393)

=xtdb-submission-outcome-correlation/observe-one-submission!= captures a
single adapter call once. A public =submit-tx= ID is *ID-only submission
evidence* and does not prove a commit. A public =execute-tx= TransactionKey
can expose a transaction ID and system time; an independently queried, pinned
=xt.txs= row can corroborate those reported metadata values and committed
status in the observed ledger.

The observation node, the adapter-bound API function, and the source of the
returned transaction key are not authenticated. A substituted API function
can return an old legitimate transaction key; the ledger can agree without
the claimed operation having been submitted. Thus even a corroborated key
is not a payload delivery receipt or a causal witness. Query exceptions and
post-execution diagnostic errors must not recast the execution outcome.

** F. Classified coacquisition (v1394)

=classified-physical-acquisition/run-classified-acquisition!= executes the
original v1388 guard-corresponded typed submit *once*, inside the original
v1392 adapter observation. Its source must have exactly =:guard-source= and
=:observation-node=. It does not call the executor twice, retry, or apply
independent reconciliation.

It returns separate =:execution= and =:diagnostic= values. The execution
value contains the original controlled result or throwable and may expose
sensitive data. The diagnostic is a bounded redacted classification.

The five origin/trust classes in the v1394 diagnostic are:

| Evidence | Reported origin | Explicit trust limitation |
|----------+-----------------+---------------------------|
| Executor | =:controlled-process-local-resolved-operation= | =:process-local-unattested= |
| Typed input | =:trusted-invocation-and-construction-hook= | =:application-path-mapping-unattested= |
| Authorization guard | =:registered-callback-and-admitted-guard-links= | =:application-reader-links-unattested= |
| XTDB API | =:instrumented-adapter-call-site= | =:process-local-bound-function-unattested= |
| Ledger | =:pinned-query-on-caller-provided-node= | =:later-node-read-not-payload-attestation= |

A report status of =:bounded-coobserved-metadata-agreement= requires a
returned execution, structurally consistent controlled acquisition,
matching typed/guard diagnostics, a committed observed physical outcome,
a single returned =execute-tx= call, and a matching reported-key/ledger
comparison. This is the *strongest diagnostic outcome*, not certification.

The same report explicitly includes:

- =:actual-payload-accepted-by-xtdb? :not-established=
- =:transaction-internal-prestate :not-established=
- =:causal-attribution-to-executor-attempt :not-established=
- =:authenticated-request-or-authorization :not-established=
- =:other-physical-writers-excluded? :not-established=
- =:deployed-handler-or-route-identity :not-established=
- =:proof-status :classified-coacquisition-diagnostic-only=
- =:certificate :not-issued=, =:admission :not-admitted=
- =:transaction-authority :none=, =:authority :none=

No operator should derive a stronger Boolean =:verified?= or issue a
certificate by stripping these qualifiers.

* Next-stage plan and required gates

** v1396–v1399 — Outcome classes and ambiguous completion

- Define an explicit, conservative correspondence between resolved-operation
  =:committed= / =:rejected= / =:already-incorporated= / =:commit-unknown=
  and the public XTDB API observation/ledger states.
- Keep the difference between a synchronous API return, a later ledger row,
  and authoritative command incorporation. A definitive rejection must come
  from actual resolved-operation semantics, not from the mere class of an
  exception recorded by v1390.
- Test lost responses, asynchronous processing, replayed ledger keys, duplicate
  attempts, and post-return diagnostic failure. Do not retry automatically.
- Preserve a durable command identity and an explicit unknown state where
  neither commit nor rejection is established.

** v1400–v1411 — Single-node ordering, retries, conflicts and serial history

- Produce source-derived abstract interleavings and check finite cases with
  Recife/TLC as internal tooling, then separately exercise real XTDB conflicts.
- Investigate transaction ordering/version checks with physical observations;
  where internally authenticated prestate is unavailable, formulate a
  *conditional* serial-history refinement argument with clear prerequisites.
- Test conflicting concurrent actions and idempotent command incorporation.
  A finite test suite cannot establish a universal serializability theorem.

** Later mandatory closure before stronger certification

- Derive a checked mapping from both nine-obligation taxonomies to the exact
  dependency graph and trusted physical witnesses each would require.
- Prove or explicitly delimit complete mediation of every protected writer,
  including alternate raw XTDB, scheduled jobs, initializers and deployment.
- Determine whether an independent backend payload/commit receipt can be
  obtained; otherwise express necessary physical semantics as explicit trusted
  backend assumptions and prove the conditional refinement theorem.
- Establish complete protected physical write/frame scope and independent
  semantics correspondence; perform adversarial counterexample searches.
- Bind certified source, runtime artifact and actual deployed handler identity
  before declaring production application assurance.
- Keep finite Recife exploration separate from universal rule soundness and
  browser-realization correspondence. Do not require downstream applications
  to write Recife/TLA+/Quint artifacts.

* Handover and operational requirements

- Next numbered revision is *v1396*, outcome classification and progression.
- Keep Gesso v1394 =:execution= private and never log full command plans,
  authenticated contexts, domain data or throwable payloads wholesale.
- Keep =:certificate :not-issued=, =:admission :not-admitted=,
  =:transaction-authority :none= and =:authority :none= at this boundary.
- Maintain immutable origin classifications and report exact unknowns rather
  than introducing implicit boolean or coercive success statuses.
- Preserve the single-invocation, no-auto-retry property of v1394.
- A process-local captured =:returned= does not establish a commit by itself.
  A later matching =xt.txs= row does not establish payload provenance.
- When the proof requires complete writer coverage, a submitted operation
  vector (even observed at the adapter) cannot substitute for enumeration and
  mediation of all possible writer entry points.
- Produce each revision as a complete, atomic file replacement in one
  uncompressed TAR with *exactly two flat regular members*: a source payload
  and the matching extensionless-stem =-commit.txt=; validate through the
  actual =ins= parser before delivering the link.
