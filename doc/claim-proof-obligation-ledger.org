** Decision for the first mechanically checked subject

Pilot exactly ONE Request and TWO competing helpers.  Check the *server-side
atomic Claim incorporation and stable command-result binding* first.  Include
membership revocation as an interfering transition and duplicate/retry of an
existing command.  Deliberately exclude Unclaim, Cancel, Reassign, transport,
SSE, DOM and liveness from the FIRST theorem; those need separate proofs and
refinement maps, not silent assumptions about this theorem.

The important theorem is NOT merely "the owner field is scalar."  The pilot
must establish that *at most one distinct initial-epoch Claim command can be
incorporated*, even with two helpers, stale preparation, retries, and a
membership-revocation race; an incorporated command's binding and recorded
outcome remain stable.  A model admitting two successful Claim incorporations
before an Unclaim/epoch change must produce a counterexample.

All Claims below refer to a single Request in an initial, still-open ownership
epoch.  A later lifecycle extension must introduce an explicit ownership epoch
or release/reopen semantics; a Request can legitimately be claimed again in a
new epoch.  No current Gesso API is claimed to generate the pilot model.

* Precise abstract machine to formalize

** State and constants

| Symbol | Kind | Semantics / origin |
|--------+------+--------------------|
| =RequestId= | constant | One Request identity; R4 Part VIII |
| =Helpers= | finite set | Exactly two distinct helpers in the first TLC instance |
| =CommandIds= | finite set | At least two command IDs and a compatible retry of one |
| =OrganizationId= | constant | Request's Organization; no independently chosen browser authority |
| =owner= | =None= or helper | Current authoritative Request owner |
| =requestStatus= | =open= or =claimed= | Persisted Request state in this first epoch |
| =memberStatus[h]= | =active= or =inactive= | Current authoritative Membership status |
| =memberOrg[h]= | Organization ID | Membership-to-Request association |
| =organizationPolicy= | finite policy value | Mutable policy determining Claim eligibility |
| =ledger= | partial function command ID -> record | Incorporated authoritative command-result records |
| =acceptedEvents= | sequence of ghost events | MODEL-ONLY audit history of accepted Claims; NOT claimed production storage |
| =attempts= | sequence or finite queue | MODEL-ONLY submitted/retried command bindings; never authoritative identity |

Each semantic command *binding* is a tuple of =command-id=,
=authenticated-principal=, =:request/claim=, and arguments containing the
Request ID.  The browser may carry its command ID and arguments, but the
principal is obtained from a trusted server context; never trust a principal
sent as browser bytes.  In the model, an attempted binding is constructed at
the trusted boundary.  If comparing to physical requests, model command-ID
validation and trusted binding are explicit separate obligations.

An accepted event has =command-id=, =principal=, =request-id=, and the
pre-commit eligibility decision.  It is a ghost variable for specifying a
history property.  It does NOT assert that existing =gesso_commands= records
persist the entire eligibility snapshot.  In particular, an accepted Claim
remains valid history if the helper's Membership is revoked AFTER the commit.

First-model assumptions to state explicitly, not infer:
- Initially Request is open/unclaimed, ledger and acceptedEvents are empty.
- Exactly one Request and one ownership epoch are modeled.
- Each server-side resolution sees a coherent *prestate* for all admission
  dependencies, and commit of the guarded Request change PLUS one durable
  command-result record is atomic/serializable.
- Only admitted resolution transitions can write the ledger or Request owner.
  The real application's other writers are NOT thereby proved absent.
- Membership revocation and Organization policy changes are serialized with
  resolution at the modeled authority boundary, not arbitrarily interleaved
  halfway through its guards/writes.
- The =AllowsClaim= predicate is a *named, application-owned* policy premise.
  The proof checks its use, not whether that policy is socially desirable or
  whether the production Clojure implementation faithfully computes it.
- A compatible retry can observe an incorporated record; a missing record is
  =unknown/unresolved= rather than proof of rejection or permission to resend
  unchanged assumptions indefinitely.

** Actions (candidate formal vocabulary)

=ClaimNew(c, h)= is admitted only when there is NO incorporated record for =c=
and the trusted binding is for =h=, =:request/claim= and this Request.
Eligibility must be checked against the state participating in the SAME
atomic commit:

#+begin_example
requestStatus = open
owner = None
memberStatus[h] = active
memberOrg[h] = OrganizationId
AllowsClaim(organizationPolicy, h, RequestId)
no conflicting command ledger entry for c
#+end_example

If satisfied, ONE abstract atomic transition changes:

#+begin_example
requestStatus' = claimed
owner' = h
ledger'[c] = {binding: (c,h,:request/claim,RequestId),
              disposition: accepted, outcome: accepted-claim}
acceptedEvents' = Append(acceptedEvents, matching ghost event)
#+end_example

The exact outcome shape is an application-model question; the above is not an
assertion that production records already have that schema.  A failed guard
must NOT write ownership or a success record.  Model a rejected *attempt* as
state-preserving for Request/ledger, with a non-authorizing rejection result;
the first proof does not require durable recording of every rejection.  A
separately specified policy is needed for duplicate or rejected-command IDs
that are not yet incorporated.

=Replay(c, presentedBinding)=, if an authoritative record exists, leaves
Request and ledger unchanged.  It exposes the recorded outcome ONLY after
trusted disclosure authorization and an exact binding match.  Incompatible
reuse and unauthorized disclosure never execute a fresh domain mutation.
Withheld results must not leak a record's private binding or contents.

=RevokeMembership(h)= changes membership state, not the existing ownership
history.  If it occurs BEFORE =ClaimNew=, the Claim cannot incorporate; if it
occurs AFTER =ClaimNew=, the accepted event still describes eligibility at
incorporation.  =ChangeOrganizationPolicy= similarly tests the policy race.

=EnqueueAttempt=, =LoseReply=, =DuplicateAttempt= and =DeliverAttempt= are
OPTIONAL model-environment actions for finite concurrency exploration; they
must not be confused with server authority.  The initial safety theorem may
use a finite nondeterministic choice of Claim/replay/revoke/policy actions
without modeling a full network queue.

A *successful finite TLC check* for two helpers and finite commands would

refinement obligations.  Keep the evidence classes separate.

** Concrete adversarial mutations expected to fail

- Mutant M1: remove the Request-open/current-owner guard from incorporation.
  The second helper can commit after the first; CLM-S2 fails even though
  =owner= still stores a single helper at a time.
- Mutant M2: allow an existing ledger entry to be replaced when the same
  command ID arrives with different arguments; CLM-S3 fails.
- Mutant M3: check Membership eligibility before a revocation, then write
  without validating the Membership/Organization dependencies at the commit;
  CLM-S1 fails under a revocation/claim interleaving in a *concrete two-phase*
  model.  A purely atomic specification cannot catch a concrete TOCTOU flaw
  by itself; CLM-R2 must expose it.
- Mutant M4: treat a missing command record following network uncertainty as
  definitive business rejection; violates future participant-knowledge
  obligations, not necessarily CLM-S1/S2.  Do not misclassify it as a server
  ownership-safety counterexample.

A useful first formal model MUST fail M1 and M2.  M3 belongs in the concrete
server/refinement companion; M4 belongs in the later browser/network model.

* Refinement direction and the v891/v892 evidence

Formal safety is a property of the abstract transition relation.  For a
TRANSFERRED implementation claim, define an abstraction function =alpha=
from concrete durable Request/Membership/Organization/command records (plus
trusted protocol context) to the formal state.  A suitable simulation
obligation is:

#+begin_example
InitConcrete(c0) => InitAbstract(alpha(c0))

ConcreteStep(c, c') =>
  AbstractNext(alpha(c), alpha(c'))
  OR alpha(c) = alpha(c')    ; explicit allowed stuttering
#+end_example

The relation must quantify over admitted server effects, conflicting writers,
retries, result lookup/disclosure and any execution path that can change the
abstract variables.  An observed matching plan alone is insufficient.

The existing v891/v892 controlled comparator contributes ONE useful premise:
it can compare an executor-bound captured prestate with the private state at
one chosen finite modeled occurrence, and compare the relevant modeled edge
and submitted plan under its declared scope.  It does not prove that the
physical execution started there, that every read was captured, that no write
intervened, or that the formal model's transitions are complete.  Thus it is
*local correspondence-test evidence*, not a proof of the simulation formula.

The first formal theorem should consume the *same semantic subject* as the
chosen production Claim operation, with explicit provenance and a declared
lowering/refinement boundary.  A separately hand-authored TLA Claim model
that happens to resemble an independently authored Clojure callback is useful
for discovery, but cannot satisfy Gate B without correspondence evidence.
